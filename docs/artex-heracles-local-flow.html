로컬 모드에서 ‘당뇨’ 검색을 따라가 봅니다

이 페이지는 Oracle 바인딩의 로컬(MVP) 모드를 예로 듭니다. 실제 평가할 DB 바인딩·버전은 아직 미정입니다. AES 값 암호화를 켜고 키 파일·FHE 인덱스·DB를 같은 DB 호스트에 둔 구성을 가정합니다. 같은 3명 데이터로 ① Heracles 내부 흐름, ② 세 제품의 평문 위치, ③ 침해 시 결과 순서로 봅니다.

② 세 제품 · 로컬 키를 쓰는 별도 실험 구성

같은 일을 할 때, 평문은 어디에 있나

이 페이지의 별도 가정: Heracles는 DB 호스트의 키 파일, pg_tde는 로컬 키링, QE는 앱 쪽 로컬 마스터 키를 사용합니다. 기본 비교 보드의 외부 키 제공자 구성과 구분하세요. pg_tde 로컬 키링은 개발·시험용이며, QE 공식 문서는 운영 환경에서 원격 KMS를 요구합니다. 키 위치를 바꾸면 침해 시 예상도 달라집니다.

③ 침해 시나리오 · 코드·문서 기반 예상, 실험 전

무엇이 털리면, 진단 값이 읽히나

시나리오를 고르면 세 구성의 예상 결과가 바뀝니다. 앱 호스트는 안전하다고 가정합니다.

Mode 1은 다른 배포 경계입니다. 외부 키가 없고 KMS에도 접근할 수 없는 오프라인 파일 사본에서는 보호를 기대할 수 있습니다. 그러나 함께 유출된 자격증명이나 살아 있는 데몬/KMS 호출 권한까지 평가해야 합니다. 키 분리만으로 호스트 장악 후 평문 보호가 확정되지는 않습니다.

④ 정리

로컬 모드 Heracles는 어디에 서 있나

pg_tde와 비교할 차이

AES 컬럼을 그대로 읽는 조회·테이블 덤프에서는 암호문이 유지될 수 있고, FHE 검색은 원본 컬럼을 풀지 않는 경로입니다. 다만 INSERT·인덱스 생성·decrypt 조회에서는 DB 쪽 평문이 생길 수 있습니다. 데이터와 로컬 키 파일을 모두 확보한 조건은 별도로 시험해야 합니다.

MongoDB QE와 비교할 경계

QE 보호 필드는 앱/드라이버에서 복호화하고, Local Heracles는 DB 호스트에 비밀키와 평문 검색어가 있습니다. QE도 지속 침해나 스냅샷·질의 정보의 결합 관측을 포괄적으로 보장하지는 않습니다. 검색 기능과 SQL 통합성은 각 DB 바인딩·버전의 실제 지원 범위로 별도 비교합니다.

아직 확인할 것

FHE 인덱스 파일만 보고 ‘서로 다른 값이 몇 개인지’, ‘값마다 몇 행인지’를 알 수 있는지는 enWord 엔진 소스로 확인해야 합니다. 어느 컬럼이 검색됐는지와 결과 건수는 서버가 압니다. 이 점은 Heracles 문서에 명시돼 있습니다.
