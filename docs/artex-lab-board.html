원본 레코드는 ‘내용’, 인덱스는 ‘찾아가는 길’입니다.

책 뒤의 찾아보기에서 ‘당뇨 → 101쪽, 103쪽’을 찾고 그 페이지를 펼치는 것과 비슷합니다. DB에서는 페이지 번호 대신 행을 찾는 식별자·위치를 사용합니다. 아래 ID는 설명용이며, 실제 PostgreSQL 인덱스는 행 위치 등을 사용합니다.

① 원본 레코드 · 설명용 정답
ID고객진단 ← 컬럼
101가당뇨
102나고혈압
103다당뇨

가로 한 줄 = 레코드(행). 세로 ‘진단’ = 컬럼(필드). 이 평문 표는 우리가 아는 합성 정답이며, 모든 제품의 DB 서버가 이렇게 본다는 뜻은 아닙니다.

② 일반 인덱스의 역할 · 암호화 전 개념
당뇨→101 · 103
고혈압→102

‘당뇨’인 행을 찾으려고 매번 원본 레코드를 전부 읽는 대신, 미리 만든 검색용 자료구조를 활용할 수 있습니다.

실제 인덱스의 바이트 구조를 그린 것은 아닙니다. 암호화 검색에서는 오른쪽처럼 단어와 ID를 평문 목록으로 저장한다는 뜻도 아닙니다.

“원본 컬럼 대신 검색 인덱스 사용”의 정확한 뜻
검색 조건에 맞는 행을 고르는 데 인덱스를 이용한다는 뜻입니다. 원본 레코드가 없어지는 것도, 원본 값을 보여줄 때 복호화가 필요 없어지는 것도 아닙니다. 일반 PostgreSQL도 인덱스를 사용할 수 있습니다.
같은 질문으로 세 제품을 함께 따라가 보세요.

검색 조건을 바꾸면 선택되는 행도 바뀝니다. 개념 시뮬레이션이며 실제 DB·암호 연산은 실행하지 않습니다.

초록: 암호문노랑: 평문 또는 평문 처리테두리 강조: 이번 단계에서 찾은 행
인덱스도 원본에서 만든 거라면, 결국 내용을 다 알 수 있는 것 아닌가요?

인덱스는 검색에 필요한 정보를 담습니다. 일반 인덱스는 값·순서 같은 정보를 드러낼 수 있고, 암호화 인덱스는 그 정보를 보호하면서 지원되는 검색을 수행하도록 설계합니다. 어떤 관계·결과·접근 패턴이 드러나는지는 방식마다 다릅니다. 그래서 ‘인덱스가 있다’도 ‘암호화했다’도 정보 누출이 전혀 없다는 보장은 아닙니다.

인덱스를 처음 만들고 갱신하는 과정도 따로 봐야 합니다. 원본을 어디서 읽고, 어떤 정보를 인덱스로 변환하며, 그때 평문이 어디에 존재하는지가 중요합니다.

개념 근거: PostgreSQL 인덱스 소개 · pg_tde 저장·복호화 경로 · MongoDB QE 흐름 · Heracles Local / MVP: heracles_adapter.cpp의 encryptedSearchOnly → decryptAndFindMatchedPositions(g_secret) → findRecordIdsFromMatchedPositions 및 aesDecryptLocal. 원본 컬럼 AES 복호화와 검색 결과의 복호·판정은 별개입니다. 핵심 암호 구현 미열람 / 실행 검증 전.

DB가 읽고 쓸 때 자동으로 암복호화

앱 → DB진단 = 당뇨앱은 평소처럼 SQL 사용
↓ DB가 저장할 때 암호화
디스크의 보호 대상 파일암호문
↓ DB가 읽을 때 복호화
DB 엔진 → 앱당뇨라는 값을 처리하고 조회 결과 반환
키 없이 암호화 파일만 가져간 사람에게 유용한 방어. 정상 조회 권한을 가진 사용자의 결과까지 숨기는 기능은 아닙니다.

MongoDB Queryable Encryption · QE

앱에서 암호화하고, DB는 암호문을 검색

앱 / 드라이버진단 = 당뇨 → 암호화검색할 조건도 클라이언트에서 변환
↓ 암호문 값 + 검색을 위한 암호화 정보
DB 서버의 보호 필드원본 값을 풀지 않고 지원되는 검색 수행일치하는 문서도 암호문으로 반환
↓ 결과를 앱 드라이버가 복호화
앱 / 사용자진단 = 당뇨
DB 관리자에게 클라이언트 복호화 권한이 없다면 보호 필드를 그대로 읽을 수 없도록 설계. 평문을 쓰는 앱은 별도 신뢰 경계입니다.

Queryable은 ‘검색할 수 있다’는 뜻. 구조화된 검색 가능 암호 방식이며, 모든 SQL 연산을 지원하는 범용 FHE라는 뜻은 아닙니다.

먼저, 무엇이 털린 상황인가요?

버튼은 설명만 전환합니다. 실제 서버 접속이나 공격 실행은 없습니다.

공통 전제: 보호할 필드를 실제 암호화했고 앱과 DB는 분리. 키 배치는 제품별 그대로 명시합니다: Heracles Local은 DB 호스트의 키 파일·메모리, pg_tde는 외부 키 제공자와 DB의 실행 중 키, QE는 분리된 클라이언트의 복호 권한. 로컬 키 파일이나 기존 호출 능력을 시험 대상에서 숨기지 않습니다. 무결성·삭제·가용성은 이 기밀성 비교와 별도입니다.

관객에게 보여줄 화면은 네 칸이면 충분합니다.

01 정상 서비스검색·조회가 실제로 동작

정답 레코드·반환 결과를 확인합니다. 서비스를 멈춰 놓고 안전하다고 평가하지 않습니다.

02 침해 가정획득한 권한과 파일 표시

파일 사본, DB 계정, DB OS 권한을 분리합니다. 권한 탈취 과정 자체는 이 데모의 범위 밖.

03 관측 증거평문 / 키 / 복호 능력

합성 표식과 일치하는 원본 증거를 연결합니다. 검색어·결과 메타데이터도 별도로 표시.

04 한 문장 판정조건부 보호 또는 노출

“이 권한·작업·관측 창에서 …”. 미검출, 도구 실패, 암호학적 보장을 혼동하지 않습니다.

데모 A · 파일 유출 → 실행 중 서버

1막: 키·온라인 권한 없이 암호화 파일만 복사. 세 구성의 기초 보호를 확인합니다.

2막: DB를 가동하고 검색-only → 원문 반환 조회 → INSERT → 재구축을 구분합니다. 그때마다 동일한 관측을 수행합니다.

3막: 키 파일에 접근할 수 있는 조건과 없는 조건을 분리합니다. 키 접근 차단 실험은 복제 환경에서 기존 프로세스와 재시작한 프로세스를 나눠 관측합니다.

확인할 차이: “검색에 원본 컬럼 복호화가 필요한가?”와 “DB 호스트의 키로 무엇을 할 수 있는가?”. Local / MVP의 키 로드·검색 결과 판정·AES 원문 복호화를 함께 평가.

지금 말할 수 있는 것과 아직 못 하는 것

소스로 설명 가능: Heracles Local / MVP는 FHE 비밀키를 로드해 암호문 검색 결과의 일치 여부를 판정하고, 원문 반환 시 로컬 AES 키로 값을 복호화하는 경로가 있습니다.

실험으로 좁혀야 함: 실제 사용 경로에서 어떤 키·평문·복호화 능력이 DB 호스트에 남는가.

아직 근거 없음: “서버가 장악돼도 모든 데이터가 안전”, “MongoDB QE보다 전반적으로 안전”, “메모리에서 못 찾았으니 노출 불가능”.

우리가 검증할 주장의 형태

“Heracles가 모든 상황에서 더 안전하다”보다, 배포 모드·시작 권한·처리 단계가 같은 조건에서 어떤 노출을 줄이는가를 먼저 입증합니다.

  • DB 호스트에서 장기 비밀키를 획득할 수 있는가?
  • 키 없이도 복호화 서비스를 호출할 수 있는가?

        PostgreSQL + pg_tde암호화 대상 저장 데이터는 디스크 쓰기·읽기 경계에서 암호화·복호화됩니다.DB 프로세스의 처리 상태, 실제 읽기·쓰기, 키 제공자 구성. 특정 키나 데이터가 항상 수집 가능하다고 가정하지 않습니다.
        MongoDB Queryable EncryptionQE로 보호한 필드의 암호화·복호화는 클라이언트 측에서 처리됩니다.DB 서버와 앱/드라이버 프로세스를 따로 봅니다. QE 보호 필드와 암호화하지 않은 필드도 구분합니다.

        DB와 앱을 같은 호스트에 두고 호스트 root를 주면 두 경계가 한꺼번에 넘어갈 수 있습니다. 보호 경계를 비교하려면 배치도 자체가 실험 조건입니다.

        Percona · pg_tde 아키텍처 ↗MongoDB · Queryable Encryption의 보호 범위 ↗PostgreSQL · pgbench 사용자 정의 부하 스크립트 ↗

        문서 확인: 2026.10.19. 설치할 버전·암호화 대상·구성은 아직 확정하지 않았습니다. pgbench를 쓰더라도 실제 암호화 대상 테이블을 사용하는지 별도 확인해야 합니다.

        맥에서 조율하고, DGX에서 실험한다면.

        아래는 제안 배치입니다. SSH 연결, 원격 도구, DB 설치가 완료됐다는 뜻은 아닙니다.

        SSH는 실험을 조작하는 통로

        DB에 침투한 사실 자체를 뜻하지 않습니다. 운영용 SSH 권한과 평가 대상에서 공격자에게 준 권한을 구분합니다.

        컨테이너 root, DB 호스트 root, DGX 호스트 root는 같은 조건이 아닙니다. 실제로 부여한 권한을 명시합니다.

        원격 에이전트 작업에 필요한 연결

        명령만 SSH로 보내고 파일 쓰기는 맥에 남지 않도록 Read·Write·Edit·실행의 기준 작업공간을 맞춰야 합니다.

        워커별 디렉터리실행 시간 제한출력·종료 코드증거 경로

        누가 생각하고, 누가 실행하고, 누가 확인할까?

        역할과 모델 선택은 논의 초안입니다. 이 페이지에서 선택해도 ARTEX 설정이 바뀌지는 않습니다.

        자동 검토 흐름 제안

        현재 코드에서 확인한 흐름

        Worker 완료 → 결과 저장 → Planner 깨우기 → 후속 계획 / 목표 판단

        Worker 완료만으로 Main이 자동 답변하지 않습니다. Main은 사용자 메시지로 실행됩니다.

        만들고 싶은 흐름

        Worker → 독립 검토 → 필요시 재실행 → 주요 결과·전체 완료를 Main이 보고

        매 워커 완료마다 비싼 모델을 깨우기보다, 중간 상태는 알림으로 묶고 중요한 결과를 요약하는 방안을 논의합니다.

        실험을 움직이는 작은 도우미

        정해진 시나리오를 일정하게 재생. 매 요청을 LLM이 생성할 필요는 없습니다.

        관측·증거 수집기

        부하 시각, 자원 사용, 로그, 산출물 참조를 한 실험 ID로 연결.

        환경 초기화

        같은 데이터·설정으로 복구. 캐시 상태와 이전 실행의 영향을 기록.

        다음 대화에서 하나씩 정해 보자.

        완성된 보고서가 아니라 생각을 모으는 자리입니다. 여기서 이야기해 주시면 본문과 시나리오에 계속 반영하겠습니다.

        아래 선택은 내 브라우저 메모

        첫 실험의 윤곽

        합성 데이터는 제안이며, 실제 데이터 사용 계획은 아직 확인하지 않았습니다.

        우리 대화의 현재 위치

        사용자가 선택

        우선 Heracles Local / MVP를 기준으로 비교. 단계별 시각화·탈취 시나리오·실험 초안을 로컬 키 경로에 맞춤. 모드 변경은 설명 기준이며 실제 서버 설정은 변경하지 않았습니다.

        사용자가 명시

        자체 운영·점검 허가 환경. 저장 파일 유출·DB 관리자·호스트 장악에 따른 노출을 비교하고 싶다.

        최근 논의

        DGX에서 sudo/root 권한을 확보한 조건으로 시험. 에이전트가 내부에서 코드를 작성하고 반복 검증하는 원격 작업공간을 구상 중.

        오늘 추가

        상용 서비스처럼 활발히 조회·갱신하는 조건이 필요할까? 서비스 부하와 관측 타이밍을 독립 축으로 추가.

        제품 소스 확인

        Heracles 145caef의 연동 코드 확인. 외부 KMS의 키 보관과 DB 호스트의 복호화 권한을 분리하고, 사용 경로별 노출을 비교하기로 제안.
