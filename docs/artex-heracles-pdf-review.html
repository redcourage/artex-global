P1 05쪽 · FHE · KMS · 정책

검토 의견일반적인 KMS 전체가 “판정·복호를 대신”하는 것처럼 보이고, “대부분 KMS와 정책”이라는 비중도 실측 전입니다.

왜 중요한가pg_tde의 키 제공과 Heracles의 원격 복호는 다릅니다. FHE가 주는 계산 중 평문 불필요성도 요청 제한과 별도로 설명해야 합니다.

교체 문구 제안FHE: 원본을 복호하지 않는 검색 계산. 원격 키 사용 구조: 계산 호스트에 복호 키를 배포하지 않음. 정책: 주체·대상·수량별 요청 통제. 각 효과는 별도 대조 실험으로 확인한다.

P0 07쪽 · 열쇠 사용 위치

검토 의견Heracles DB 칸의 “암호문 + 공개키” 색상은 현재 평문 경로를 숨깁니다. pg_tde “기동 시”도 과도한 단순화입니다.

왜 중요한가Mode 1에서도 검색어, encrypt 입력, decrypt 출력, 재색인·일부 INSERT 원문이 DB 호스트를 지납니다. QE의 보호 질의 값은 클라이언트에서 변환됩니다.

교체 문구 제안Heracles DB: 암호문 검색 계산 + 평문 검색어 + 경로에 따른 원문 입출력. pg_tde: 필요 시 principal key 조회·캐시, 내부 키로 DB에서 처리. QE: 클라이언트에서 보호 값·질의 값을 암호화.

추가·확인할 내용키의 종류를 구분하세요: pg_tde principal/internal key, QE CMK/DEK, Heracles FHE secret/AES DEK/evaluation key. “키 없음”은 복호 키 없음으로 표기합니다.

P1 08쪽 · Mode 1 검색 흐름

검토 의견검색 전용 경로는 잘 설명했지만, “선택적 원문 보기”가 보안적으로 작은 부가 기능처럼 보입니다.

왜 중요한가허용된 원문 복호 API가 같은 호스트에서 접근 가능하면 공격자는 검색을 우회해 그 경로를 사용할 수 있습니다. 또한 알려진 검색어와 반환 ID의 연결 자체가 민감 값을 알려줄 수 있습니다.

교체 문구 제안검색만 수행하는 경로에서는 원본 AES 컬럼을 복호하지 않는다. 그러나 원문 복호 경로와 검색 결과에 의한 값 추론은 별도의 노출 경로다.

추가·확인할 내용상단은 검색어→암호 연산→판정→ID, 하단은 AES 암호문→KMS→평문→데몬→DB→앱의 동등한 크기 흐름으로 그리세요. 현재와 향후 분리 설계를 다른 색으로 표시합니다.

P0 09쪽 · 네 가지 검색 방식

검토 의견“값당 토큰 하나”, “n-gram을 따로 저장해야 함”이 일반 명제처럼 적혀 있습니다.

왜 중요한가Heracles는 splitWords=false일 때 값 전체가 한 토큰이며 길이 제한이 있습니다. 토큰 하나가 암호문 한 개·고정 크기라는 뜻은 아닙니다. 원격 HMAC+ngram은 선택한 대조 구성이지 비FHE 검색 전체의 유일한 방식이 아닙니다.

교체 문구 제안선택한 Heracles 토큰화 구성과 원격 HMAC+ngram 구성을 같은 검색 의미로 비교한다. 태그 수 감소가 실제 누출 감소로 이어지는지는 별도로 검증한다.

추가·확인할 내용QE는 2026-09-29 접두·접미·부분 일치 GA 발표가 있습니다. 실험 릴리스·드라이버·길이·정규화 조건을 고정하세요. 지원 여부, 저장량, 보안 누출을 별도 열로 나눕니다.

P1 10쪽 · 보관함과 창구

검토 의견비유는 유지하되 QE가 “마스터 키를 꺼내 줌”으로 읽히지 않게 해야 합니다. “내보내는 API 없음”의 확인 수준도 필요합니다.

왜 중요한가QE에서는 CMK가 원격에 남아도 풀린 DEK가 클라이언트에서 사용됩니다. Heracles 비반출은 내부 문서의 계약이며, HE-KMS 구현과 배포 설정의 독립 확인은 아직 없습니다.

교체 문구 제안pg_tde는 principal key를 받아 내부 키를 사용하고, QE는 외부 KMS로 DEK 포장을 풀어 클라이언트에서 사용한다. Heracles는 판정·값 복호를 원격에서 수행하도록 설계돼 있다.

추가·확인할 내용원격 복호와 키 export 금지를 구분하세요. KMS의 백업·복구·관리 API, 디버그 경로, 운영 권한과 메모리까지 확인해야 배포 수준 비반출을 주장할 수 있습니다.

P0 11쪽 · KMS 흔적과 회수

문서에 새로 넣어야 할 내용

1. 신뢰 경계 지도

앱, DB 엔진, 플러그인·데몬, KMS, 검증기를 별도 상자로 표시하세요. 각 시나리오에서 공격자가 장악한 상자만 붉게 칠합니다. DB root를 줬다고 KMS root까지 준 것은 아닙니다.

같은 DGX의 컨테이너 분리는 DGX 호스트 root로부터의 독립 경계로 간주하지 않습니다.

2. 원문과 검색 인덱스

Heracles의 원문 AES 암호문과 FHE 검색 인덱스를 두 줄로 그리세요. FHE 검색 점수의 복호와 원문 AES 복호는 다른 연산입니다.

동형암호라는 이름만으로 AES 경로·메타데이터·권한 설계가 함께 안전해지지는 않습니다.

3. “보여 주지 않음”의 의미

원문 바이트를 읽지 않았어도 “행 101의 진단은 당뇨”를 알아냈으면 속성 노출입니다. 반대로 문자 집합이나 그룹 크기를 얻은 것만으로 모든 원문을 복원했다고 볼 수 없습니다.

동일한 “검색”을 비교하는 조건

Exact / Prefix / Substring / Range를 이름만 맞추지 말고, 문자열 길이·쿼리 길이·공백·대소문자·한글 정규화·NULL·중복·반환 ID·결과 제한을 맞춥니다. Heracles 문서상 기본 토큰 길이 45 코드포인트와 splitWords 설정을 기록합니다. QE는 선택한 릴리스의 문자열 검색 제한을 적용합니다. 공통 부분집합은 보안 비교에 쓰고, 한쪽만 지원하는 기능은 별도 기능 비교로 남깁니다. [H1] [M4] [M5]

능동적 침해에 대한 한계

현재 초안은 주로 기밀성입니다. “모든 표면”이라는 표현을 유지하려면 결과·인덱스 변조, 오래된 스냅샷 재생, 서비스 중단 시의 동작도 별도 축으로 다뤄야 합니다. FHE 계산 그 자체가 결과의 진실성·최신성·완전성을 보증하는 것은 아닙니다. 이번 범위를 유출에 한정한다면 무결성·가용성 전체를 평가한 것이 아님을 명시하는 편이 정확합니다.

기본 구성제품이 원래 제공하는 키 배치·기능·권한. 같은 정상 업무를 허용.

모든 제품에 똑같은 “KMS 복호 횟수 제한”을 걸 수는 없습니다. 어떤 구성은 앱/DB가 키를 받아 로컬 복호하므로 해당 집행 지점이 없습니다. 동일한 정책 목표와 실제로 집행되는 경계를 기록하고, 추가 프록시·복호 서비스가 필요하면 별도 구성으로 표시합니다. KMS 없는 FHE나 검색 기능이 없는 암호화와의 비교로 기능 차이를 숨기지 않습니다.

AI 실험에서 고정할 항목

  • Planner / Executor / Reviewer의 모델·버전·프롬프트·도구·초기 문서와 소스 접근 수준. reviewer에는 공격자가 볼 수 없는 정답 데이터 접근을 분리.
  • 같은 벽시계 예산뿐 아니라 모델 토큰·도구 호출·성공한 질의 수를 기록. 비용 자체를 보안 지표로 사용하지 않음.
  • 독립 세션과 새 합성 데이터로 반복. 실행 순서를 섞고 성공 사례만 선택하지 않음. 사전 합의한 반복 수와 분포·불확실성을 보고.
  • 암호 기능을 우회하는 평문 적재·복호·정비 경로도 시도 대상에 포함. KMS 자체 장악을 제외했다면 명시.
  • 이미 알려 준 검색어·시드·평문 fixture를 “새로 탈취”한 값으로 집계하지 않음. 데이터는 공격자가 모르는 holdout 표식과 실제적인 값 분포를 함께 사용.
  • 외부 모델에는 원본 DB 자료 대신 필요한 관측 요약을 전달. 모델 API로 전송된 데이터를 내부 반출 시나리오의 성공으로 오인하지 않도록 제어 경로와 수신 경로 분리.

  2. 조건: 세 제품 배치도와 공격자의 시작 권한. 어떤 구성은 파일 유출, 어떤 구성은 호스트 장악인지 구분.
  3. 같은 업무: 검색 ID 반환 / 원문 조회 / 지속 쓰기. 동일 정답과 허용 사용자.
  4. 원문·질의·키의 경로: 세 제품을 같은 기호로 나란히. Heracles AES/FHE 두 경로 표시.
  5. 현재 확인된 차이: 코드·문서상 보호 경계와 남은 복호 능력. 실제 우위로 확대하지 않음.
  6. 누출 지도: 파일·메모리·온라인 관측·원문 반환·검색 결과의 각 정보.
  7. FHE 가설: H1·H2·H3의 지지/기각 조건. 현재와 향후 버전 분리.
  8. 시험 설계: A0/A1/A2/B1/B2/B3, 정책 대조군, 동일 질의·독립 판정.
  9. AI 워크플로: 계획→실행→증거→검증, 실패 분류와 반복 조건.
  10. 결과 화면: 제품 순위를 채우지 않은 측정 템플릿. 실행 후 같은 발판 패널에 분포 표시.
  11. 주장 기준: 설계 확인 / 실행 검증 / 비교 실측에 따라 허용 문구.
  12. 제품 과제: 현재 gap, 원문 복호 경계 분리, 질의 프라이버시, 정책 집행. 수행 우선순위.

발표에 바로 쓸 수 있는 핵심 문장

Heracles는 원본 값 보호와 검색 계산을 분리하고, 지정된 FHE 검색 경로에서 원본 컬럼의 복호 없이 일치 결과를 계산하도록 설계돼 있다. Mode 1은 복호 비밀키를 DB 호스트 밖에서 사용하지만, 현재 원문 복호·적재·재색인 경로와 평문 질의는 별도 노출 경로로 남는다. 우리는 동일한 침해 조건과 업무 기능에서 이 구조가 pg_tde 및 MongoDB QE 대비 어떤 정보를 더 보호하는지 실험으로 검증한다.

아직 쓰면 안 되는 결론: “FHE라서 모든 AI 공격에 안전하다”, “태그가 적어서 더 안전하다”, “회수하면 이미 유출된 데이터도 안전해진다”, “AI가 못 찾았으니 유출할 수 없다”.

시각 자료 자체의 수정

  • 주황=평문, 파랑=암호문, 보라=키처럼 의미를 고정하고 ‘안전’ 색으로 쓰지 마세요. 한 호스트에 평문·암호문이 함께 있으면 두 색을 함께 표시합니다.
  • 표 12·14·21쪽의 작은 조건 문구는 각주로 숨기기보다 행을 분리합니다. 발표 화면에서 조건이 읽히지 않으면 본문 단정만 전달됩니다.
  • 설계 사실·코드 확인·실측·계획을 같은 모양으로 그리지 않습니다. 특히 현재 Mode 1과 미래 Mode 1.5/2를 같은 실선으로 연결하지 않습니다.
  • 19쪽의 정해진 제품별 선은 빈 패널 또는 제품명 없는 예시로 교체합니다. 예상 방향이라도 독자는 결과로 기억할 수 있습니다.
  • 본편은 12~15쪽 정도로 줄이고, 나머지는 상세 근거·조건·실험 계약 부록으로 옮기면 주장과 한계가 더 잘 전달됩니다.
