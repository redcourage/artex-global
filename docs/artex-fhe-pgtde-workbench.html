pg_tde와 Heracles를 비교하며 FHE 인덱스의 이득을 찾는 작업 페이지입니다. 현재 Mode 1과 계획된 Mode 1.5를 구분해 함께 논의합니다.

이번 논의의 중심

“키를 외부에 보관한다”에서 한 걸음 더.

원본은 AES로 보호하면서도,
원본을 풀지 않고 Exact / Substring 검색을 할 수 있다는 점이 어떤 침해 상황에서 유리한지 확인합니다.

검색과 원문 열람을 분리할 수 있는 능력, 그리고 실제 제품에서 그 권한이 분리돼 있는지는 별개의 질문입니다.

01 · 우리가 입증하고 싶은 것

FHE의 직접적인 이득은
검색 계산을 위해 원본을 복호하지 않아도 된다는 것

원본 AES 암호문과 별도로 만든 FHE 인덱스에서 비교를 수행하고, 매치 결과로 행 ID를 찾습니다. 원본 데이터의 복호 권한을 검색 계산과 분리할 수 있는 기반입니다.

pg_tde

저장 암호화

파일을 암호화하고, DB는 사용 시 테이블·인덱스 데이터를 평문으로 처리합니다. 일반 검색에 사용하는 자료는 DB 안에서 평문입니다.

매 질의마다 전체 테이블을 복호한다는 뜻은 아닙니다. 인덱스만 읽는 검색도 있습니다.

Heracles Mode 1

암호문 인덱스 검색

원본 AES 컬럼을 풀지 않고 FHE 검색을 수행합니다. KMS가 검색 결과를 판정하고 DB가 일치 ID를 얻습니다.

현재 검색어는 평문이며, 매치 ID·결과 수·일부 메타데이터도 보입니다.

제품 전체의 보호

복호 권한은 별도 문제

검색에 원문이 필요 없어도 같은 호스트에서 원문 복호를 요청할 수 있다면, 공격자가 그 경로를 사용할 수 있습니다.

Mode 1.5는 이 원문 복호 능력을 클라이언트 측으로 분리하려는 계획입니다.

주장 초안
“Heracles는 원본을 복호하지 않고 검색을 수행한다. 우리는 이 특성이 DB 내부의 원문 노출을 얼마나 줄이고, 어떤 침해 조건까지 효과가 남는지 검증한다.”
“PostgreSQL도 컬럼을 AES로 암호화하면 되는 것 아닌가?”

맞습니다. 원본 암호화 자체는 FHE의 차별점이 아닙니다. 추가 질문은 그 원본을 평문으로 공개하지 않으면서 필요한 검색까지 제공하는가입니다.

컬럼을 암호화한 뒤 DB에서 풀어 검색하는 방식, 평문 검색용 보조 자료를 두는 방식, 별도의 검색 가능한 암호 구조를 쓰는 방식은 노출이 다릅니다. Exact 검색에는 blind index 같은 대안도 있으므로 “검색 가능 = FHE만 가능”이라고 주장하지 않습니다. 부분 일치에서도 기능·누출·추론 조건을 실제로 비교해야 합니다.

우선 비교: pg_tde와 Heracles의 보호 범위. 추가 대조: 필요한 경우 같은 PostgreSQL에서 컬럼 암호화와 검색 처리 방식을 바꿔 FHE 기여를 더 구체적으로 확인합니다.

근거: Percona pg_tde Architecture · Heracles overview.md §1.2·1.4, kms-integration-mode1.md §3.

02 · “꺼내기”와 “복호하기”는 다르다

DB는 암호문을 그대로 꺼내 줄 수도 있습니다

아래 버튼으로 검색만 할 때와 사용자가 원문을 볼 때를 비교하세요. Mode 1.5 열은 문서상 목표 흐름이며 실행 검증된 구현이 아닙니다.

어떤 작업인가요?

평문을 다루는 단계암호문을 다루는 단계별도 키 서비스

키 재료가 없다

DB 호스트에 FHE 비밀키·AES 키를 배포하지 않는다는 뜻입니다. 키가 없더라도 외부 복호 서비스를 호출할 권한은 남을 수 있습니다.

원문 복호 능력이 없다

키도 없고, 원문을 대신 복호해 주는 경로도 사용할 수 없다는 뜻입니다. DB root에 대해 이 속성을 주장하려면 권한 집행을 DB 밖의 신뢰 경계에서 해야 합니다.

Mode 1도 키는 외부 KMS에 있는데 왜 평문이 DB에 보이나요?

현재 원문 조회 경로는 AES 암호문 → KMS 복호 → 데몬 → DB → 앱입니다. 실제 AES 복호는 KMS에서 일어나지만, 반환된 평문은 DB 호스트 메모리에 들어옵니다. 로컬 모드와 혼동한 설명이 아닙니다.

FHE 검색에서는 원문 AES 복호가 필요 없습니다. 그러나 heracles.decrypt를 통한 원문 열람, 일부 적재·재색인 경로는 별도로 평문을 다룹니다.

03 · 어떤 상황에서 더 유리할 수 있나

공격자의 능력을 바꾸면 결론도 달라집니다

아래 내용은 현재 구조에서 예상하는 평가 관점입니다. 실제 공격 성공·실패 결과가 아닙니다.

현재 가장 직접적인 FHE 비교 장면: 동일한 검색 업무를 수행하는 동안 DB에 어떤 원문·검색 자료가 평문으로 존재하는지 확인합니다. 다만 메모리 관측에서 원문을 못 찾은 것은 부재의 증명이 아니며, 해당 검색 경로에 원문 복호가 필요 없다는 코드·실행 근거와 함께 해석해야 합니다.
04 · 처음에는 이 정도만 해보자

같은 검색을 제공하며,
알려 주지 않은 원문이 얼마나 드러나는가?

데이터

같은 합성 문자열

두 제품에 같은 행 ID와 보호 문자열을 넣습니다. 알려진 검색 조각과 공격자가 모르는 나머지 부분을 구분합니다.

기존 검색어 자체를 맞혔다고 새 데이터 탈취로 세지 않습니다.

업무

Exact / Substring → ID

먼저 원문을 반환하지 않는 검색을 실행합니다. 결과 ID가 독립 정답과 같은지 확인합니다.

문자열 길이·정규화·공백·중복·결과 제한을 맞춥니다.

공격 목표

미지 원문과 속성 복원

직접 평문 획득과 검색 결과를 이용한 추론을 각각 측정합니다. 파일·메모리·온라인 호출 결과를 구분합니다.

허용된 검색 기능 자체가 추론 통로가 될 수 있습니다.

진행 순서할 일다음 단계로 넘길 증거
1 · 정상 동작동일 데이터·질의로 같은 ID를 얻는지 확인정답률, 지원 질의, 사용 버전·설정
2 · 검색 전용파일과 검색 시점 메모리의 노출 관측미지 원문·키·질의·메타데이터 관측 범위
3 · 온라인 침해실제 DB 호스트에서 접근 가능한 SQL·복호 경로 확인복호 가능 여부와 경로별 원문 노출
4 · 서비스 확장원문 조회·INSERT·재색인 부하 추가검색 전용 조건과의 차이, 정상 서비스 영향
5 · AI 자율 실행같은 권한·도구·문서·예산으로 반복하고 고정 스크립트와 대조실제 행동·독립 검증 결과·종료 이유

최초 실험은 소규모로 정답과 경로부터 확인합니다. AI가 도구를 못 쓰거나 모델 한도가 끝난 경우는 보안 성공이 아닙니다. 벽시계 예산뿐 아니라 유효 요청 수와 정상 처리량도 기록해 속도 차이와 보호 효과를 구분합니다.

구현 전 확인할 제약: 현재 내부 문서는 Heracles PostgreSQL 바인딩을 유지보수 중단 MVP로 설명합니다. Mode 1을 PostgreSQL에 곧바로 적용할 수 있다고 가정하지 않습니다. 실행 가능한 바인딩으로 구조를 먼저 비교할지, 동일 PostgreSQL 구성을 보완할지는 아직 결정하지 않았습니다.
05 · 내부 문서에 실제로 있는 계획

Mode 1.5는 원문 복호를 클라이언트 측으로 분리합니다

문서 상태: TBD구현 완료로 취급하지 않음
“동형암호 복호(검색용 인덱스)를 맡는 KMS-1은 DB Host와, AES 복호(조회용 원문)를 맡는 KMS-2는 Client와 연결한다. DB Host는 검색용 인덱스 복호화는 가능하지만, 원문 복호화 능력을 갖지 않는다.”

~/cryptolab/heracles/docs/internal/spec/architecture.md:111 · 기준 commit 145caef. 여기서 검색용 복호는 매치 판정을 위한 경로로 읽어야 하며 원본 AES 복호와 구분합니다.

구분현재 Mode 1Mode 1.5 계획
FHE 검색 판정DB·데몬 ↔ 외부 KMSDB·데몬 ↔ KMS-1
원본 AES 복호DB·데몬 ↔ 외부 KMS클라이언트 ↔ KMS-2
DB의 원문 복호 능력데몬 소켓을 통해 요청 가능갖지 않게 하는 것이 목표
현재 검색어 평문DB 호스트를 통과이 분리만으로 해결되지 않음. CC-SEARCH는 별도 과제
구현 상태문서상 O, 배포·실행 확인 별도문서상 TBD
GAP-1: 쓰기 경로도 함께 바뀌어야 합니다

문서는 현재 KMS 모드에 client AES 수단이 없어 heracles.encrypt로 원문이 SQL·extproc·데몬을 지난다고 설명합니다. Mode 1.5 또는 AES DEK 외부화 시 클라이언트 암호화로 바꿀 예정입니다.

따라서 원문 조회만 분리했다고 모든 평문 경로가 사라지지는 않습니다. 적재·재색인·로그·오류·우회 호출까지 포함해 목표 경계를 확인해야 합니다.

06 · 우리가 다음에 정할 것

현재 제품을 입증할지,
원하는 보호 경계를 먼저 만들지

현재 Mode 1 평가

검색 중 원문 노출 감소를 확인

기존 복호 능력이 남는 한계를 포함해 평가합니다. “원본 복호 없이 검색한다”와 “호스트 장악 후에도 원문이 안전하다”를 분리합니다.

Mode 1.5 목표 평가

검색 권한과 원문 열람 권한을 분리

DB 호스트가 원문을 복호할 수 없는 경계를 먼저 구현·검증한 뒤, 검색 기능이 유지되는지와 침해 후 추론 범위를 평가합니다.

정상 사용자는 일치 ID만 필요한가, 최종 원문까지 읽어야 하는가? 앱과 복호 서비스는 어느 경계에서 신뢰하는가?
