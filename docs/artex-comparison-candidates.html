비교 기준: pg_tde + 외부 키 관리 ↔ Heracles Mode 1 + 외부 HE-KMS. 두 구성 모두 같은 합성 보호 값과 같은 검색 정답을 사용합니다. 현재 구현을 먼저 평가하고, 원문 복호 경계를 분리한 미래 설계는 별도 후속 구성으로 둡니다.

먼저 입증할 질문

검색 업무를 수행하는 DB에서 원본 값을 평문으로 처리해야 하는가? 공격자가 DB 파일·메모리를 얻었을 때 어떤 원문·키·관계를 추가로 확보하는가?

FHE의 직접 기여: 지정된 검색 계산에서 원본 AES 컬럼 복호를 필요로 하지 않는다는 점.

함께 보여 줄 한계

현재 Mode 1의 DB 호스트는 원문 AES 복호를 요청할 수 있습니다. 파일·메모리에 키가 없다는 사실만으로 살아 있는 root 공격자의 데이터 접근이 막히지는 않습니다.

적재·원문 조회·재색인의 평문 경로와 검색 결과의 추론도 별도 포함합니다.

보조로 평가할 질문

접속 차단 후, 훔친 자료만으로 추가 복원이 가능한가? 권한 회수 후 온라인 복호가 얼마나 계속되는가?

이 차이는 주로 키 사용 위치·회수 구현의 효과입니다. FHE 고유 효과로 합치지 않습니다.

첫 실행 · 검색만

검색, 원문 조회, INSERT가 함께 발생합니다. 원문이 실제 반환되는 서비스에서 평문 노출이 얼마나 달라지는지 확인합니다.

세 번째 · 정비

재색인·복구·키 회전·장애 상황. 정상 검색에서 보인 보호가 정비 경로에서도 유지되는지 별도 확인합니다.

처음부터 상용 규모 부하를 만들 필요는 없습니다. 소규모에서 정답·관측·공격 경로를 확인한 뒤 데이터량과 동시성을 늘립니다. 느린 검색 때문에 시간 안에 처리한 행이 적은 결과는 암호적 보호와 구분해야 합니다.

같은 PostgreSQL 위에서 비교하면 가장 깔끔하지만, 현재 Heracles PostgreSQL 바인딩은 문서상 유지보수 중단 MVP입니다. 분석한 Mode 1을 PostgreSQL에서 바로 실행할 수 있다고 가정하면 안 됩니다.

현재 구현을 빠르게 검증

Mode 1 실행을 확인한 Heracles 바인딩과 Percona PostgreSQL+pg_tde를 비교합니다. 암호 경로·보호 경계의 구조 비교이며, DB 엔진 차이가 있어 일반 성능·취약점 수의 직접 순위는 내리지 않습니다.

같은 DB에서 엄밀히 비교

Heracles PostgreSQL의 필요한 모드·기능을 먼저 검증·보완합니다. 구현 과제가 추가되지만 DB 엔진·질의·권한을 더 잘 맞출 수 있습니다.

권장 순서

현재 실행 가능한 바인딩으로 구조와 한계를 먼저 확인하고, 차별화 가설이 남을 때 같은 DB 구성에 투자합니다. 아직 배포나 포팅을 수행한 것은 아닙니다.

주장 후보: “Heracles의 지정된 검색 경로는 TDE 기반 일반 검색과 달리 원본 컬럼의 복호 없이 일치 결과를 계산한다. 이 차이가 DB 호스트 침해 후 원문·키·추론 정보의 노출을 얼마나 줄이는지는, 정상 복호 경로까지 포함한 동일 조건 시험으로 확인한다.”

현재 그대로 주장할 수 없는 것: “DB root를 빼앗겨도 평문을 얻을 수 없다.” 현재 Mode 1의 원문 복호 능력이 남아 있기 때문입니다.

pg_tde가 실행 중 평문을 사용하는 것은 결함이 아니라 저장 암호화의 보호 범위입니다. 이번 비교는 제품 취약점 순위가 아니라 침해 후 데이터 보호 범위 비교입니다.

“침해 성공”과 “원본·키 획득 성공” 사이에 어떤 경계가 남는가?

현재 판단: Heracles Mode 1의 유력한 보호 특성은 계산 호스트의 원본 복호화 필요성을 줄이는 것과 복호화 비밀키를 그 호스트에 배포하지 않는 설계입니다. 이 둘이 모든 공격 경로에서 데이터 유출을 막는다는 뜻은 아니며, QE보다 전반적으로 강하다는 근거는 아직 없습니다.

① 검색 중 원본 노출 감소

같은 검색을 수행할 때 계산 호스트에 원본 컬럼을 풀어 둘 필요가 있는지 확인합니다. pg_tde 대비 차이를 보일 수 있지만 QE도 보호 필드의 서버 측 평문 복호화 없이 검색합니다.

측정: 검색 전용 실행에서 관측된 원본 필드·레코드 범위. 적재·원본 조회·검색어 평문은 별도 기록.

② 키의 외부 재사용 제한

공격자가 가져간 파일·메모리에서 사용 가능한 데이터 키를 얻어, 키 서비스 접근 없이 추가 데이터를 풀 수 있는지 확인합니다. Heracles의 비반출이 실제로 성립한다면 제품 구조상의 강점 후보입니다.

측정: 획득 키의 종류·범위, 오프라인 추가 복원량. 이것은 원격 키 사용 구조의 효과이며 FHE만의 효과로 분류하지 않습니다.

③ 검색 자료의 정보 노출

암호화 인덱스·매핑·질의 관측만으로 값의 관계나 원본을 얼마나 추론하는지 비교합니다. 여기에서 QE보다 노출이 작다는 근거가 나오면 FHE 검색 방식의 추가 가치를 주장할 수 있습니다.

상태: 미확인. enWord 엔진·인코딩·인덱스 메타데이터·허용 검색 결과의 누출 분석이 먼저 필요합니다.

3. 성공·실패 한 칸 대신 네 가지 결과를 남깁니다

원본 값

어떤 필드·몇 개 레코드를 정확히 복원했는가? 검색 대상과 비검색 대상을 구분합니다. 복사한 파일 크기와 평문 복원량은 다릅니다.

검색어와 메타데이터

검색어, 일치 ID, 결과 수, 반복 질의 연결, 파일 크기 등의 관측을 나눕니다. 원본 값을 얻지 못해도 정보 노출은 있을 수 있습니다.

키와 복호화 능력

키를 얻었는가? 키를 추출하지 않고도 복호화 함수를 호출할 수 있는가? 현재 결과만 읽는지, 다른 레코드도 풀 수 있는지 구분합니다.

결과 한 줄 예시 형식:
제품·버전 / 키 배치 / 시나리오 / 작업 / 관측 시간 / 복원 필드·레코드 수 / 키 획득 / 복호화 호출 가능 여부 / 증거 참조 / 한계
판정은 “복원 확인 / 이번 조건에서 미검출 / 도구 오류 등으로 판정 불가”로 나눕니다.

실험마다 새 합성 표식을 만들고, 실행 주체에게 기준 정답을 미리 주지 않습니다. “당뇨”처럼 이미 알고 있던 검색 문자열을 출력했다고 데이터 복원 성공으로 세지 않습니다. 독립 검증기가 기준 데이터와 획득 결과를 대조합니다. 무암호화 대조군으로 수집·검증 절차가 실제 평문을 찾을 수 있는지도 확인합니다.

4. 서비스 부하와 비용은 같은 조건에서 붙입니다

각 작업을 처음 읽기 → 반복 읽기 → 읽기·쓰기 혼합 상태에서 비교합니다. 검색 전용 상태를 볼 때는 원본 조회나 데이터 적재의 평문이 이전 실행에서 남은 영향을 통제합니다. 메모리에서 한 번 못 찾은 결과는 평문 부재의 증명이 아닙니다.

같은 자원·요청률·결과 정확도에서 p50/p95 지연, 처리량, 메모리와 저장 크기를 기록합니다. 앱·드라이버·키 서비스의 비용도 포함하고, 기능 미지원은 보안 실패가 아닌 미지원으로 표시합니다. 초기에는 보안 경계 확인을 먼저 하고 데이터 규모를 늘립니다.

공정한 비교를 위해 고정할 배치
Heracles는 Local / MVP, 원본 AES 활성, 로컬 키 경로를 기준으로 합니다. pg_tde의 keyring 또는 별도 provider, QE의 앱·CMK 위치를 결과마다 명시합니다. 모든 구성을 같은 호스트에 몰아놓은 경우와 앱/키 영역을 분리한 경우는 다른 실험입니다. 현재 Heracles Local에는 지원되지 않는 키 분리 배치를 임의로 가정하지 않습니다. DB 바인딩이 다르면 성능 차이에 엔진 차이도 포함됩니다.

Heracles Local을 기준으로 특히 조심할 해석
현재 읽은 코드에는 DB 호스트에 FHE 비밀키·AES 키를 로드하는 경로가 있습니다. 반면 QE·Acra·CipherSweet는 복호화 영역을 DB 호스트 밖에 배치할 수 있습니다. 따라서 DB 호스트 root만 확보한 조건에서는 이들이 더 유리할 가능성도 있습니다. 키 배치 효과를 FHE 자체의 효과와 분리하고 실제로 검증해야 합니다.

현재 추천: Heracles Local + pg_tde + MongoDB QE의 비교 골격은 유지합니다. 엄밀한 OSS 실험을 먼저 하고 싶다면 Acra를 우선 추가하고 QE는 별도 트랙에서 수행합니다. CipherSweet는 비교를 단순화하거나 앱 수정 비용·후처리 비용까지 알고 싶을 때 추가합니다. 네 대상 모두를 한꺼번에 구축할 필요는 없습니다.

필수 조건

설치할 바이너리·이미지·의존성을 준비한 뒤, 실험 환경 안에서 DB·키 관리·암호화 검색을 실행할 수 있을 것. 외부 서비스 계정이 실행의 필수 조건이 아니어야 합니다.

별도 확인

한 바이너리로 실행되는지, 여러 프로세스·컨테이너가 필요한지 표시합니다. “자체 호스팅 가능”이 “하나의 프로세스”를 뜻하지는 않습니다.

보안 경계
